# Apply recipient-specific information requirements

## Actor

[[Private renovator]] deciding what an architect, consultant, general builder or individual trade
needs from the project.

## Main flow

1. The plugin reads the chosen purpose, recipient profile and selected project scope.
2. It presents required, helpful and professionally-produced information separately.
3. Architect/design profiles emphasize objectives, existing conditions, constraints, budget,
   priorities, desired spatial outcomes, evidence and open questions.
4. General-builder quotation profiles emphasize coordinated scope, drawings or references,
   quantities, specifications, dependencies, site conditions and a structured commercial reply.
5. Individual-trade profiles emphasize spatial targets, trade-owned work, prerequisites,
   interfaces, relevant products, access and expected completion evidence.
6. The renovator may add a project-specific request without changing the reusable profile.

## Extensions

- **2a** — A profile asks for a domain capability not yet available. The item is shown as
  unavailable or attachable evidence, never as an empty satisfied requirement.
- **3a** — The recipient says another item is needed. The renovator adds it to this handoff; the
  profile itself changes only through a separate reviewed product-content update.
- **5a** — One work package spans several trades. Each recipient sees the shared interface and
  only the responsibility relevant to that package; no copied work package is created.

## Guarantee

Recipient profiles filter and explain one canonical project model; they never create recipient-
specific copies of rooms, work, quantities, costs, decisions or evidence.

## Out of scope

- Professional calculations, drawings, specifications or method statements.
- A fixed national list of trades or professional titles.
- Claiming that a profile is sufficient for a permit, tender or contract.

## Acceptance criteria

1. Requirement items are classified as required, helpful or expected back from a professional.
2. Architect, general-builder and individual-trade profiles produce visibly different emphasis.
3. Every included project fact links to its canonical stable identity.
4. Unavailable capability is distinct from missing information.
5. Project-specific requests do not mutate the reusable profile.
6. Shared scope remains one work identity across every recipient package.
