# Inclusive usability and evaluation memo

Research date: 2026-09-13. Scope: consolidate the existing desktop Obsidian 2D editor so a first-time private renovator can complete useful work with confidence. This memo proposes acceptance criteria and a research protocol; it contains no new interviews, participant observations, live accessibility audit, or measured usability results. Repository inspection baseline: `4ca4c7ea77e72e3ce4ea631884b353662d69964a`. Live evidence is owned by the parent increment report.

## Decision to carry into the increment

Make the first complete editing loop understandable: identify the right plan, create one room, correct its dimensions, recover a mistake, and recognize that the result is saved. Preserve the existing precision and advanced operations, but reveal them where the selected object and current task make their purpose clear. Treat visible instructions, readable controls, predictable focus, and alternatives to fine dragging as the usability of existing functions. Do not add a separate “senior mode,” compulsory tutorial, new planning capability, or new schema.

“Approachable for my grandmother” is a useful aspiration for independence, not a persona definition. Age, computer experience, confidence, vision, dexterity, language, and renovation knowledge vary independently. An older participant may be the most experienced planner in a study; a younger participant may need enlarged text or an alternative to dragging. Recruit and report those dimensions explicitly. WAI identifies overlap between older users’ needs and established accessibility needs, rather than a single age-specific interface prescription. [WAI older users overview](https://www.w3.org/WAI/older-users/).

## Research implications for this editor

**Support independence without hiding control.** W3C cognitive accessibility guidance recommends understandable purpose, familiar language, clear steps and support for recovery; it is a Working Group Note, not additional WCAG conformance requirements. Apply it here as one concise instruction for the active task, persistent field labels, and a visible way to stop. Preserve user input when explaining an error. Do not require remembering instructions from an earlier onboarding screen. [Making Content Usable](https://www.w3.org/TR/coga-usable/), 2021-04-29.

**Reduce simultaneous decisions while keeping discovery possible.** Shneiderman’s multi-layer interface paper proposes an initial subset that can expand as users learn. It supports testing staged complexity, but it does not prove that hiding this editor’s tools improves success. For this increment, retain recognizable task families and stable locations. Keep Cancel, Finish, selection identity and saving state readily available; place specialist properties within the existing relevant inspector. Avoid a novice/expert mode switch that users must understand before starting. [Original paper, University of Maryland repository](https://drum.lib.umd.edu/items/90921200-6f02-4f5b-904a-34b87dba9895), paper title dates 2003; repository record dates 2005. Confidence: medium for principle, unmeasured for this application.

**Do not make exactness depend on hand stability.** Findlater and colleagues studied 20 adults aged 61–86 and 20 aged 19–51 on pointing, dragging, crossing and steering. Their controlled tasks found different costs across interaction types; desktop steering was particularly demanding for the older group. The study used 2013-era equipment and most participants used computers daily. It does not establish a universal size or justify replacing the desktop editor with touch. The relevant inference is to test fine target acquisition and sustained dragging separately from task comprehension, using participants’ normal devices. [Findlater et al., CHI 2013 author-hosted paper](https://makeabilitylab.cs.washington.edu/media/publications/Findlater_AgeRelatedDifferencesInPerformanceWithTouchscreensComparedToTraditionalMouseInput_CHI2013.pdf). Confidence: high for that experiment; medium for transfer to renovation editing.

**Provide alternative operation, not merely shortcuts.** Keyboard access and single-pointer access without dragging are separate requirements. A numeric field usable with pointer clicks and typing can help both, while an arrow shortcut alone does not satisfy a pointer-only non-dragging requirement. Straight lines, endpoint positioning and resizing are not automatically exempt from keyboard operation just because they appear on a drawing canvas. [Keyboard, SC 2.1.1](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html); [Dragging Movements, SC 2.5.7](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html).

## Accessibility requirements and scope of claims

Use WCAG 2.2 A/AA as the technical target for the editor’s applicable web interface. Do not call this a conformance audit or certification. The host also affects access, so record plugin-owned failures separately from host behavior. [WCAG2ICT](https://www.w3.org/TR/wcag2ict/), Group Note 2025-12-11, offers informative guidance for non-web software; it does not itself create new normative requirements.

| Requirement | Standard distinction | Editor verification |
|---|---|---|
| Pointer targets | [2.5.8, AA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html): 24×24 CSS px or applicable exceptions, including defined spacing/equivalence. [2.5.5, AAA](https://www.w3.org/WAI/WCAG22/Understanding/target-size-enhanced.html): 44×44 CSS px, with its exceptions. 44px is this increment’s preferred core-control design target, not the AA minimum. | Measure active regions rather than icon graphics or device pixels. Zooming the canvas does not repair a deficient toolbar target. Document densely positioned geometry separately; do not apply an “essential” exception to the whole editor. |
| Drag alternatives | [2.5.7, AA](https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements.html) requires a single-pointer alternative without dragging unless dragging is essential or user-agent-controlled. [2.1.1, A](https://www.w3.org/WAI/WCAG22/Understanding/keyboard.html) separately requires keyboard operation, subject to the path-dependent-function exception. | Inventory create, select, move, resize, rotate, calibration endpoints and panel resizing. Verify existing forms/buttons meet both needs; close any gap as access to that existing action. Do not claim drawing is categorically exempt. |
| Accidental activation | [2.5.2, A](https://www.w3.org/WAI/WCAG22/Understanding/pointer-cancellation.html) permits different cancellation/undo approaches; it is not a blanket requirement for a confirmation modal. | Check press/move/release, release outside target, pointercancel and focus loss. Prefer reversible commit and Undo where already supported. Preserve intentional single-click actions. |
| Text readability | [1.4.3, AA](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html): text 4.5:1, qualifying large text 3:1, with defined exceptions. [1.4.4, AA](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html): text resizing to 200% without loss of content or functionality, subject to its exceptions. | Check actual default light/dark and custom-accent themes, errors, units and hints. Do not use placeholders as labels. A proposed comfortable body size is a design choice, not a WCAG-mandated font size. |
| Controls and visual state | [1.4.11, AA](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html): required control/state and graphical information generally 3:1 against adjacent colors, with defined exceptions. | Check selection, handles, input boundaries, error states and relevant plan graphics on both plan/image backgrounds. | Zoom/reflow | [1.4.10, AA](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html): reflow at 320 CSS px width for vertically scrolling content, with an exception for parts whose use/meaning requires two-dimensional layout. | The spatial plan may need two-axis navigation. An unsupported-pane message alone does not demonstrate retained functionality. |
| Focus | WCAG [2.4.7, AA and 2.1.2, A](https://www.w3.org/TR/WCAG22/); [2.4.11, AA](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html) prohibits the focused component being entirely hidden by author-created content. | Show a visible indicator, logical sequence and a reliable exit. | Semantic feedback | [4.1.3, AA](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html) covers programmatically determinable status messages without focus transfer; [3.3.1, A](https://www.w3.org/WAI/WCAG22/Understanding/error-identification.html) covers identifying/describing detected input errors. | Announce selection/task/save results at meaningful transitions; associate errors with fields and retain values. | Names and navigation | [WCAG 2.2](https://www.w3.org/TR/WCAG22/) includes name/role/value, label-in-name, meaningful sequence and input labeling requirements. [APG toolbar guidance](https://www.w3.org/WAI/ARIA/apg/patterns/toolbar/) is an informative interaction pattern, not a separate conformance requirement. | Prefer native semantics. ## Proposed novice evaluation protocol

### Recruitment and study design

Run two formative rounds of six participants each, fixing the highest-impact problems between rounds. Proposed quotas across the 12 people: at least eight new to this editor and without CAD practice, at least six self-reporting low confidence with unfamiliar software, at least six aged 65 or older, and at least four who do not use Obsidian regularly. Categories overlap; they are not diagnoses. Include at least two confident experienced users to detect whether consolidation makes common work harder. Do not recruit only friends of the maker or productivity-tool enthusiasts.

Add four to six paid accessibility sessions covering low vision/enlargement, keyboard-only or alternative pointer use, and screen-reader use. Some may overlap the novice sample; record that rather than inflating the count. Seek more than one person for each access method where possible. These numbers support formative discovery, not statistical representation or a population success-rate claim. WAI advises combining user involvement with standards evaluation and avoiding generalization from a few people. [Involving users in evaluation](https://www.w3.org/WAI/test-evaluate/involving-users/), updated 2021-06-01; links updated 2024-04-30.

Screen by ordinary activity: recent renovation involvement, device/keyboard language, normal zoom settings, familiarity with drawing tools, and “How confident do you feel trying a new computer program?” on a 1–5 scale. Ask what accommodations help, not for medical history. Do not infer impairment from age. Let participants use their normal glasses, mouse, trackpad, assistive technology and breaks. Do not disable accessibility settings to standardize the study.

Book 60 minutes with an optional break; allow a longer slot or split sessions when requested. Pay for the booked session even if the software blocks progress. Use a synthetic project, dimensioned reference and fake notes. Explain that the software is being tested and that stopping is useful feedback. Obtain separate consent for observing, recording screen/audio and retaining quotes. A support person may help with setup if requested; record assistance during measured tasks.

First establish that the participant can access the supplied desktop and use their ordinary input method on a neutral screen. Provide a brief description of Obsidian’s tabs and the sample project, but do not teach the editor’s controls. Record host setup effort separately; it is a real adoption issue, but not the editor task timer. Pilot the protocol with two people excluded from release-gate counts to remove broken fixtures and leading wording.

### Task script and observable outcomes

Prompts name a goal rather than the control to click. Tasks must be confirmed reachable in the baseline and candidate builds. Skip unsupported functionality with an explicit reason instead of adding it to satisfy a script.

| Task | Neutral prompt | Completion evidence and probe |
|---|---|---|
| T1: orient | “Here is the project for the sample apartment. Show me where you would work on the ground-floor plan.” | Correct project/floor open. Ask “What could you do here first?” Record first meaningful action, wrong destinations, and whether the participant understands which plan is active. |
| T2: first room | “Add a kitchen that is 3.5 metres wide and 4.2 metres deep. Name it Kitchen.” | Exactly one committed room with correct name/dimensions; not just a drawn preview. Allow any supported route. Observe the initial path, unit interpretation and finish discovery. |
| T3: exact correction | “The second measurement was wrong: make the depth 4 metres, keeping the width the same.” | Correct saved dimensions and no accidental movement of another object. Ask how they knew which dimension changed. |
| T4: recover | “You have changed your mind about that last change. Put the room back as it was.” Then, on a reset disposable fixture: “Remove this spare room. Now bring it back.” | Correct Undo outcome, room identity retained where the contract requires it, no unintended deletion. Observe whether recovery can be found without remembering a shortcut. |
| T5: navigate | “Look closely at this corner. Now show the whole floor again.” | View changes without geometry changes; full scene restored. Ask whether zoom changed real measurements. Use mouse or trackpad as normal. |
| T6: interrupt and return | “Read the note in the other tab, then return and continue changing this room.” Narrow the pane through the moderator’s agreed test setup. | Correct context, selected room and field recovery. Note clipping, focus loss and any work the participant must repeat. Test deliberate pause before and after commit separately. |
| T7: save confidence | “You are finished for today. Show me how you would know the room will be here when you return.” | Participant correctly interprets save state; close/reopen verifies data independently. For a failure fixture, they recognize the unsuccessful/paused state and choose an available safe next action. |
| T8: reference extension | “This drawing has a marked four-metre distance. Make it usable as the plan background.” | Correct source and known-distance calibration, coherent dimensions, committed reference, recovery from one invalid entry. Secondary task with its own denominator; do not let import difficulty obscure the first-room loop. |
| T9: existing advanced regression | “Place the existing door/opening in this wall and set its specified position,” or an already supported rotation task. | Experienced and access-method participants reach the same existing result. Select one bounded task after inventory; this is a regression guard, not a new feature request. |

Give the task in writing and read it if requested. Keep it available. Use light concurrent think-aloud only when comfortable; do not penalize silence. If an action is ambiguous, ask afterward “What did you expect to happen?” Avoid “Did you see the Add button?” and other coaching. Define an assistance ladder: repeat goal → neutral encouragement → directional hint → exact instruction → moderator completes. Any directional or exact hint makes the attempt assisted. At distress or a requested stop, end immediately; do not turn an observation interval into pressure to hurry.

Record start at the end of the task prompt and stop at verified task outcome. Record interruptions, assistance and recovery separately. A long pause can mean reading, planning, fear or inaccessible content; do not label it confusion without follow-up. Use practical moderator review points (for example two minutes without a meaningful action), then ask whether they want to continue; these are not automatic task-failure deadlines.

### Measures and proposed release thresholds

Every threshold below is proposed and unmeasured. Agree it before the candidate round; do not revise it after seeing results to manufacture a pass. For the final formative round, use counts and case descriptions alongside percentages. Six participants cannot estimate a 90% population success rate.

| Measure | Definition | Proposed decision rule |
|---|---|---|
| Core loop independence | T1–T4 and T7 completed correctly with no directional hint. Report each task’s denominator and complete-loop denominator. | At least 5 of 6 final-round novices complete the full loop independently; remaining failure must be understood and triaged. Any serious loss or wrong-object destructive change blocks release regardless of average. This is a formative gate, not population proof. |
| Exactness and units | Saved geometry agrees with task, using the product’s precision/rounding contract. | Zero unnoticed magnitude/unit errors; a wrong-unit interpretation triggers copy/field review even if corrected after a hint. |
| Recoverability | User discovers a supported recovery and returns to the intended state. | At least 5 of 6 independently recover a change; no unrecoverable committed-data loss in any observed or controlled run. |
| State comprehension | User describes current plan/selection, preview versus saved, and next useful action in their own words. | At least 5 of 6 correctly explain state at the predefined probes. A false belief that a failed save succeeded is a release blocker. |
| Task ease | After each task, custom 1–7 scale from very difficult to very easy; report distributions. | Proposed median ≥5 for core tasks with no unresolved recurring rating ≤2. Do not label this a validated questionnaire or combine unlike tasks into a misleading score. |
| Confidence | Pre/post custom 1–5 question about doing this task alone later. | Inspect change and reasons; target at least 5 of 6 rating ≥4 at the end. This is supporting evidence, never a substitute for correct performance. |
| Time and effort | Time to first useful room; action count, wrong turns, failed drags and assistance. | Establish baseline first. Proposed improvement target: reduce median first-room time by 25% with no accuracy/access regression; report samples and confounds. Do not impose a “fast enough for older adults” time limit. |
| Accessibility | Manual criteria, keyboard routes, actual AT behavior and controlled failure cases. | Zero unresolved blocking access failures in the scoped core loop. Every claimed route has actual evidence on the stated environment. A working pointer journey cannot compensate for a blocked keyboard route. |
| Relearning | Optional follow-up after 7–14 days, if participants consent. | At least 5 of 6 returning novices reopen and make one correction without directional help. If fewer return, report exact count and treat as exploratory; no invented completion. |

Baseline/candidate comparison needs different first-time participants matched as far as practical on confidence, tool experience and access needs. Reusing participants for both builds measures learned performance, not first-use improvement. With small samples, show individual trajectories and recurring problems; do not claim statistical significance. A later confirmatory study can be powered once baseline rates and the smallest meaningful difference are known.

## Native Obsidian matrix and separation from browser proof

Record OS, Obsidian/plugin build, input device, keyboard layout, theme, viewport CSS size, actual leaf content width, OS scaling, host interface zoom, canvas zoom, assistive technology/version and fixture id. Do not call a screenshot “460px” based only on the outer window.

Run the critical loop in a normal single leaf; a 460px constrained leaf beside a Markdown note; and both sides of 900px/400px boundaries. Add host zoom at 100%, 200% and 400%, independently of canvas zoom and Windows display scaling. Use both default themes and at least one supported custom accent; test English and German including decimal entry and longer labels. Test keyboard-only and normal mouse/trackpad first, then representative AT sessions. This is a risk-based matrix, not a requirement for every possible Cartesian combination.

Native-only probes include Ctrl/Cmd+P with Add or an inspector open; host hotkeys on Shift+1/Shift+2; Space press/release; middle-button behavior; returning from Alt-Tab; two simultaneous plan leaves; focusing a hidden tab; screen-reader interaction/browse-mode transition at `role="application"`; and focus/selection after overlay dismissal. Test Sticky Keys with existing modifier paths. A host shortcut conflict must be recorded with the configured binding; do not declare it impossible merely because `stopPropagation` exists in source.

Browser verification remains useful for actual layout, target measurements, contrast, pointer sequences, input semantics and automated accessibility checks. Unit/DOM tests establish logic. Native Obsidian establishes host integration. Participant sessions establish learnability and comprehension for those participants. Keep these evidence classes separate in both test records and release language.

## Local-first measurement and privacy

Prefer a moderator worksheet and synthetic fixtures for the first study. No production telemetry or analytics service is needed. If temporary instrumentation improves timing accuracy, confine it to an explicitly enabled research/harness build and store events locally. Its implementation would be a later authorized test task; this planning branch does not add logging.

Proposed minimal event schema: random session id, build id, task id, relative monotonic timestamp, enumerated action category, start/success/failure outcome, input method supplied by the study configuration, layout class and enumerated error code. Record transaction completion rather than every pointermove. Do not collect vault paths, project/room names, notes, photos, reference content, raw keystrokes, coordinates, account identifiers, device fingerprints or inferred disability. An Undo is not automatically an error; the task and follow-up interpretation determine its meaning.

Store consent/contact information separately from task observations with a restricted linking key. Offer observation without audio/video recording. Capture only the synthetic project window; pause before navigating personal notes or system notifications. Let participants review retained quotes and request deletion. Proposed retention: delete raw recordings within 30 days of synthesis and identifying recruitment records when follow-up/compensation completes; retain anonymized issue summaries and aggregate counts only. Confirm retention in the consent text before recruitment. Vault-local files can still be synced or backed up, so keep research records outside personal/shared vault sync by default and document any deliberate export. No recording, recruiting message or external upload has occurred for this memo.

## Required handoff for the increment

The synthesis should select a small first release slice from IU-01–IU-10 based on its captured live evidence. Each selected item needs a current before-state, proposed behavior, acceptance method and owner. Keep accessible alternatives and accurate saving/recovery ahead of cosmetic simplification. Preserve existing advanced operations and exact editing contracts while reorganizing their presentation.

Before calling the increment successful, attach: actual core-loop results with participant counts and assistance; native environment/run records; keyboard/AT outcomes and unresolved limitations; measured target/contrast/reflow checks; and candidate-build identification. Update historical test cases only for their current triggers and executed outcomes. Until those records exist, describe this as a researched usability plan with proposed gates, not a validated redesign.
